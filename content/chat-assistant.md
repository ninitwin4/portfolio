## What It Is

The chat on this site is a retrieval-augmented generation system - RAG. It answers questions about Ni Ni's work using only documents she wrote, not the language model's general knowledge. Ask it something outside that corpus and it declines rather than guessing.

The corpus is hand-written markdown: one document per project, plus background and a career history. Site copy is deliberately not the source. The site is skimmable and finished; the bot needs what sits underneath it - the numbers, the tradeoffs rejected, what broke.

## How Retrieval Works

At build time, a script splits each document into chunks on its section headings, normalising size by merging sections that are too short to stand alone and splitting any that run long. Each chunk keeps its document title and section name as metadata, so an answer can cite a place a reader recognises.

Each chunk is then converted into an embedding - a vector of numbers positioning that text in a semantic space where related passages sit near each other. Those vectors are written to a JSON file committed to the repository.

At question time, the question is embedded the same way, and cosine similarity ranks every chunk against it. The top few are passed to the model as the only material it may answer from, along with their sources. This is why the assistant can say "I don't know" - if nothing relevant is retrieved, there is nothing to answer from.

## Why No Vector Database

Vector databases earn their keep at roughly 100,000 chunks and up, where scanning everything becomes too slow and you need approximate nearest-neighbour indexing. This corpus is a few dozen chunks. A linear scan over an array in memory is faster than a network round trip to a hosted store, adds no service to run or pay for, and cannot drift out of sync with the repository.

The retrieval step is isolated behind a single function with a narrow interface, so moving to pgvector later means rewriting that one file rather than the system around it. Choosing the small thing on purpose, and leaving a clean seam where the big thing will go, is the actual decision - not the absence of infrastructure.

## Being Honest About Scale

At the size this corpus started, retrieval was not strictly necessary. The whole thing fit in a single model prompt with room to spare, and simply including every document - context stuffing - would have answered just as well.

It was built as retrieval anyway, for two reasons: the corpus is meant to grow past the point where stuffing stops working, and the code is identical at both scales. Knowing which problem you do not yet have, and building for the one you will, is different from cargo-culting an architecture. The decision is recorded with that reasoning in the repository's DECISIONS.md.

## Evaluation

Retrieval quality is measured, not assumed. A golden question set pairs realistic questions with the source that should answer each, including out-of-scope questions the assistant must decline. Scoring against it gives retrieval recall - the share of questions where the correct source reached the top results.

This matters because nearly every RAG failure is a retrieval failure in disguise. The model looks like it is hallucinating when in fact the right chunk never reached it. Measuring retrieval separately from generation is what tells the two apart.

## Voice

The assistant speaks about Ni Ni in the third person and never impersonates her. A portfolio bot that writes as "I" invites a reader to mistake generated text for something she actually said.

## Stack

Next.js 15 App Router, TypeScript, Tailwind v4, deployed on Vercel. Embeddings from OpenAI's text-embedding-3-small, generated at build time. Answers generated by the Anthropic Claude API. No database and no vector store.
